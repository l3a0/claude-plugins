# A pull request review round

The owner's rules ask that every pull request is reviewed by blind lenses before the owner reads it. A round of that review takes the same steps every time, and a session that works them out again pays for it in tokens. On 2026-11-03 review rounds on companion pull requests in three repositories worked out the brief, the lens prompts, the verifier grouping and the comment format again each time. This file holds that procedure.

`SKILL.md` stays the one definition of how roles are seated, prompted and verified, and of what a review comment must hold. This file adds what a round needs around those steps, and points to `SKILL.md` by step number rather than restating it:

- one brief that every lens reads,
- one round covering several companion pull requests,
- fixes applied to every companion,
- the order of pricing, posting and handover,
- the body's `## Revision` section and the owner's rulings.

A review that a session cannot finish can go to a new session on `templates/handoff-brief.md`. Around 2026-11-04 UTC three sessions were started the same way to finish reviews, each brief written from nothing.

The session that owns the branches runs the round, as the pull request review that lens mode names as its first caller. It runs `SKILL.md`'s steps 2 to 4 itself, in the same session, as lens mode allows, and launches the roles beside the completeness and over-reach lenses, and on a design the reader lens, in one blind round.

A round can cover several pull requests at once. A rule adopted from one source often lands in three repositories, such as l3a0/ithildin-runtime, this plugin and l3a0/repo-template. One brief covers all of them, every lens reads all of them, and a finding that one copy contradicts another surfaces in the same round. The worked examples are the review comments on [l3a0/ithildin-runtime PR #25](https://github.com/l3a0/ithildin-runtime/pull/25), [PR #26](https://github.com/l3a0/ithildin-runtime/pull/26) and [PR #27](https://github.com/l3a0/ithildin-runtime/pull/27), with their companions [l3a0/claude-plugins PR #46](https://github.com/l3a0/claude-plugins/pull/46), [PR #47](https://github.com/l3a0/claude-plugins/pull/47) and [PR #48](https://github.com/l3a0/claude-plugins/pull/48), and [l3a0/repo-template PR #74](https://github.com/l3a0/repo-template/pull/74), [PR #75](https://github.com/l3a0/repo-template/pull/75) and [PR #76](https://github.com/l3a0/repo-template/pull/76).

1. Write the brief.
2. Choose the lenses.
3. Run the blind round.
4. Verify.
5. Apply the fixes to every pull request.
6. Price the round and decide whether another follows.
7. Post the review comment.
8. Record the revision and the owner's rulings.

## 1. Write the brief

Every lens reads one brief file, so each lens prompt stays a few lines long and every lens starts from the same facts. Copy `templates/review-brief.md` to `<scratchpad>/review-r<N>/brief.md`. The brief stays in the scratchpad and is never committed, because it names local checkouts and may name a copyrighted source.

Fill the subject list with the script beside this file, one argument per pull request:

```bash
python3 <this skill>/scripts/brief_anchors.py l3a0/ithildin-runtime#27=<checkout> l3a0/claude-plugins#48=<checkout>
```

It prints each pull request's head commit and the merge base its diff starts from, which it reads from GitHub's compare API rather than the base branch's tip. It flags a checkout whose `HEAD` is not the head commit, since a lens reading that checkout would review other code, and a pull request that is no longer open. Replace each `<What it changes.>` with the files and sections the pull request touches.

The template's sections say what else the brief holds: the facts every lens would otherwise spend turns finding, how to check a source, the limits every agent in the round works under, and what is out of scope. A source helper, such as one that prints the passage around a phrase at a location, comes with the source rather than with this skill.

A later round's brief anchors at the fixing commit and lists the owner's rulings since the last round as facts. It names what the round reads: the diff from the last round's anchor to the fixing commit, leaving out what a merge of the base brought, and any passage or function that diff touches or that states the same fact. Where a fix touches the path to an irreversible action, the round reads that path from its entry to the action. The brief names the files that hold that path, and `git diff --name-only` on the fix decides whether it touches them, not the session's judgement. Where a fix rewrites the subject rather than patching it, the round reads the whole change again. The price is that a lens can miss a fault in text no fix touched, which round 1 has already read. The reason is cost: on [l3a0/ithildin-runtime PR #51](https://github.com/l3a0/ithildin-runtime/pull/51) every round re-read the whole change at about 15 US dollars. On [PR #83](https://github.com/l3a0/claude-plugins/pull/83) the rounds told to read only the fix cost 1.70 to 5.14 US dollars against 8.42 to 11.38 before, though those rounds also seated fewer lenses, and cost per lens fell from 1.75 to 1.13 US dollars. The brief does not list the earlier rounds' findings, so each lens reads the change rather than a list of past answers. It does carry forward `## Out of scope`'s list of owning work and the questions still waiting, after re-reading each one and re-running the template's searches, because a stale line there tells a lens to leave a settled question alone. A question the owner has settled moves to the facts, and where a pointer's owning work closed without stating the guarantee, the guarantee goes back into the rule, and any other gap into an issue. A list that stops being none takes the template's paragraphs back.

## 2. Choose the lenses

Run the completeness and over-reach lenses `SKILL.md`'s step 2 names, and on a design or architecture doc or a design pull request its reader lens, as general-purpose agents, and seat the roles and the required seats by the same step. Each role runs as its own agent, with `subagent_type` set to `l3a0:team-<role>`. The 2026-11-03 rounds ran between five and eight lenses.

A round run this way follows lens mode's run limit, as `SKILL.md`'s lens mode says: the roles and the verifiers stay under ten runs in each round, and the completeness, over-reach and reader lenses are the caller's own.

From round 2 on, seat the completeness and over-reach lenses, on a design the reader lens, and each role whose objective the fix can hurt, by `SKILL.md`'s step 2 as applied to the fix rather than to the change. A required seat still sits when the fix touches its path. Any other role whose area no fix touched sits out, and the comment names it and what the fix was searched for.

## 3. Run the blind round

Launch the lenses as `SKILL.md`'s step 3 says. Give each spawn a description starting with `review <tag> r<N> `, where the tag is the main pull request's number, such as `review 49 r1 risk-engineer`. The `l3a0:loop-cost` skill finds transcripts by that description once their paths are gone, and the tag keeps two subjects reviewed in one session apart.

A role's prompt carries the six things `SKILL.md`'s step 3 lists. The brief holds the subject, the charter, the files to read and what is out of scope, so the prompt names the brief's absolute path for those and adds the role's scratch folder, `<scratchpad>/review-r<N>/<role>/`. A completeness, over-reach or reader lens prompt carries the same and its question. It also carries the finding format block from `SKILL.md`'s step 3 in full, and the limits in the brief written out, because a general-purpose agent has no agent file to supply them and holds every tool and the session's GitHub login. Every prompt asks for a reply with the evidence for each finding cut to the command and the line that shows it, under 1,500 words in round 1 and 500 after it, naming anything it left out. The prompt also limits a lens that mutates code to 20 mutants in round 1 and 6 after it, because a survivor proves a gap at the tenth mutant as well as at the sixtieth, and the lens finishes within its own turn and names each behaviour it did not mutate. These are starting numbers rather than measured ones. Neither limit binds the path to an irreversible action or a guarantee `templates/review-brief.md` keeps.

## 4. Verify

Read every finding together, and merge the ones that rest on the same fact into one, crediting each lens that raised it. A finding three lenses raised is still one finding, and the comment names all three.

Then verify by `SKILL.md`'s step 4, including its rule for grouping and its limit on what the session may check itself. On [l3a0/ithildin-runtime PR #25](https://github.com/l3a0/ithildin-runtime/pull/25) one verifier reran the lenses' scripts, one read the owner's rulings on the issue tracker, and one checked citations against the source. Describe each verifier `review <tag> r<N> verify <topic>`, give it the brief's path, and write out the brief's limits in its prompt. Each returns one verdict per finding.

1. **CONFIRMED**, with the command and its output.
2. **REFUTED**, with what it ran that shows the claim false.
3. **PARTLY**, with which part held.

With each verdict it gives the kind the finding deserves and the smallest fix. A verdict can raise a finding's kind, or lower it, as well as refute it. One round on [l3a0/ithildin-runtime PR #26](https://github.com/l3a0/ithildin-runtime/pull/26) lowered three must-fixes to should-fix, because something the repository already held covered each one, such as a hard limit or mutation testing. The comment then gives the lower kind and what lowered it.

Where the session weighs cutting a sentence an earlier round of this review added, or moving or cutting a passage under step 5, for a veto or must-fix, give its verifier that resolution, any confirmed finding that text answered, and one more question: which of that text must stay for the limits and rules the brief names, the vetoes in the role agent files or the charter, and the guarantees `templates/review-brief.md` keeps in full to hold, in the exact sentences it would keep and with any price, and does that leave any finding open as a contradiction rather than as build detail. That move or cut goes to a verifier even where one command would confirm its finding. On [l3a0/ithildin-runtime PR #29](https://github.com/l3a0/ithildin-runtime/pull/29), [round 8](https://github.com/l3a0/ithildin-runtime/pull/29#issuecomment-6620866314) asked this about the journal comparison and [round 10](https://github.com/l3a0/ithildin-runtime/pull/29#issuecomment-6621337006) about the contract suite's sentence. Round 8's answer kept the definition of a journal store that is behind, and round 10's kept the clause that the suite's orders never reach a strategy's positions.

Ask step 5's question of a fix that would add a new kind of record or stored state before writing a verifier's prompt, confirming its finding by command, or applying a verifier's fix. A veto, must-fix or should-fix that question changes to read an existing record goes to a verifier, even where one command would confirm its finding, and the verifier says what the new record would have done that the read does not, and what rows already in that record would do under the new reading. A note's fix changed this way gets no verifier. A read that does not serve is not applied. On a should-fix it is a fix that does not hold, as the next paragraph says. A veto or must-fix still needs its fix under `SKILL.md`'s step 5. Anything else the read gives up is a price the comment names.

A should-fix whose fix would change a limit, a halt condition, a record, an order of steps or a permission goes to a verifier too, with the fix the session means to apply, because a fix is text no lens has read. It joins the verifier already reading that file where there is one, and where the run limit binds, vetoes and must-fixes go first. The verifier also says whether the fix holds. A refuted should-fix is dropped with its fix, apart from step 5's cut of a sentence an earlier round added. A fix that does not hold is not applied, and the session applies the verifier's corrected fix, which the comment names as read by no one else, or lists the finding under `### Left alone` with the reason. A verdict that raises the finding to a veto or a must-fix counts under step 6 like any other. On [l3a0/ithildin-runtime PR #51](https://github.com/l3a0/ithildin-runtime/pull/51), a should-fix in [round 8](https://github.com/l3a0/ithildin-runtime/pull/51#issuecomment-6677897032) on an order that only reduces a position drew the veto of [round 9](https://github.com/l3a0/ithildin-runtime/pull/51#issuecomment-6678310251). Other should-fixes and notes get no verifier. The session reads each one, applies it when it is cheap and inside the change's scope, and otherwise lists it as left alone with the reason. Work outside the pull request's scope is filed as its own issue and linked under `### Left alone`. A question only the owner can rule on, such as one `SKILL.md` sends to the board, a change to a role's vetoes, two confirmed vetoes that no one fix can satisfy, a conflict with an open proposal that a veto disputes, or a question the brief's `## Out of scope` sends to the owner, goes under `### For the owner`, and those two vetoes wait as `SKILL.md`'s step 5 says. On [l3a0/ithildin-runtime PR #28](https://github.com/l3a0/ithildin-runtime/pull/28), the rule on resending a lost cancel was allowed in rounds 2 to 4, forbidden in round 5 and sent to the owner only in round 6.

## 5. Apply the fixes to every pull request

Before editing, write down for each surviving finding and each planned cut or move which of the pull requests carry what it is about, and keep the cuts and moves for the comment. A rule that lands in three repositories is fixed in all three, or the next round's completeness lens finds the copies disagreeing. The wording can differ by repository, such as a plugin's role check dropping a trading platform's names and citations, but what the rule says matches.

Before a fix adds a new kind of record or stored state to a passage, whether a lens, a verifier or the session proposed it, ask whether a record the design or the code already holds serves, meaning each reader of the new one gets what its finding needs from it, and the limits and rules the brief names, the vetoes in the role agent files or the charter, and the guarantees `templates/review-brief.md` keeps in full still hold. Where one serves, the fix reads it, and step 4 says who checks that change. A fix that still adds a record says, on its finding's line in the comment, which existing records it weighed and why each falls short. A fix that adds a record an owner's ruling or request asks for skips this question, and its line says so. A new record can draw findings of its own in every later round, and the paragraphs below act only once it has drawn them. The price of reading an existing record is that a verifier can miss a job it leaves undone, and that each reader may judge again where one stored answer would serve them all. On [l3a0/ithildin-runtime PR #55](https://github.com/l3a0/ithildin-runtime/pull/55), a recorded reason for no close drew must-fixes in rounds 9 to 12. [Round 12](https://github.com/l3a0/ithildin-runtime/pull/55#issuecomment-6695399041) cut it, because a person's switch-off was already journaled and already held the close. [Round 13](https://github.com/l3a0/ithildin-runtime/pull/55#issuecomment-6695593031) then raised three must-fixes on that cut, two of them on paths its verifier had missed. [Round 14](https://github.com/l3a0/ithildin-runtime/pull/55#issuecomment-6695844391) answered a veto by adding a journaled verdict. [Round 15](https://github.com/l3a0/ithildin-runtime/pull/55#issuecomment-6696094465) confirmed a veto against it, because execution wrote the value the gate then read, and cut it, so the gate reads the broker's message as the journal already held it. Rounds 16 to 18 then raised eight must-fixes and a veto on the gate's check, the count and the refusals, so a read is new text too.

A refuted or lowered finding on a sentence an earlier round of this review added is often a reason to cut that sentence rather than add to it, because a fix is new text the next round's lenses read. A cut takes only what the verifier's answer does not keep, and leaves a sentence that applies an owner's ruling or request, answers a confirmed finding or states a price. Any real case a cut sentence described goes on the issue that owns it, filed if none does, and the comment says what that costs. On [l3a0/ithildin-runtime PR #29](https://github.com/l3a0/ithildin-runtime/pull/29), [round 11](https://github.com/l3a0/ithildin-runtime/pull/29#issuecomment-6621582399) gave fault 20 a clause, as a should-fix, on an order that fills while execution is down. [Round 12](https://github.com/l3a0/ithildin-runtime/pull/29#issuecomment-6621791022) refuted the contradiction a lens raised against the clause and removed it anyway, because it stated an outcome no rule does. [l3a0/ithildin-runtime #39](https://github.com/l3a0/ithildin-runtime/issues/39) now holds the case, and the stated price is that a restart with a missed fill may halt until it is built.

Where a passage this change adds draws a veto or a must-fix for the second round, confirmed or lowered, and what draws them is mechanics another issue owns, fix it by moving those mechanics to that issue, leaving what step 4's answer keeps, any sentence that applies an owner's ruling or request, or states a price, and a link to the moved text. The next brief lists the issue and that link under `## Out of scope`, the link as a proposal. The price is that moved mechanics wait for their build for a full review, while what stays in the rule is still reviewed. Where no issue owns the mechanics that draw those findings, an earlier round of this review added them, and no ruling or request from the owner asked for them, cut them back the same way, with no link, even where they answered a confirmed finding. The price is that those mechanics are gone until an issue asks for them, so a confirmed finding step 4's answer leaves open as build detail goes on an issue, filed if none does. With no answer, neither paragraph cuts anything, and a finding the answer leaves open as a contradiction is fixed in the rule. Neither a removal nor a move takes out a guarantee `templates/review-brief.md` keeps in full, whatever a verifier kept: it stays in the rule or in a merged rule the rule names. [Round 8](https://github.com/l3a0/ithildin-runtime/pull/29#issuecomment-6620866314) records that rounds 6, 7 and 8 each raised must-fixes on the Startup comparison, each on the round before's fix, and only round 8 moved it to [l3a0/ithildin-runtime #32](https://github.com/l3a0/ithildin-runtime/issues/32) item 13, and round 10 moved the contract suite's switch and its drill to item 12 the same way. On [l3a0/claude-plugins PR #68](https://github.com/l3a0/claude-plugins/pull/68), a procedure the review itself added to this step's list drew a veto or must-fix in each of rounds 2 to 5, until [round 5](https://github.com/l3a0/claude-plugins/pull/68#issuecomment-6622839437) cut it to the two sentences below.

From round 2 on, before editing, read the earlier rounds' comments and list each passage that meets the first sentence of the paragraph above, and say for each whether it moves and, where it does not, why not. The list goes in the round's comment under `### Findings in two rounds`, on each pull request that carries the passage, and never in the next brief, because each lens reads the change rather than past answers. On [l3a0/ithildin-runtime PR #51](https://github.com/l3a0/ithildin-runtime/pull/51), the text on a halt whose write failed drew findings in rounds 11, 12 and 13, each on the fix before it, and its mechanics moved to [l3a0/ithildin-runtime #10](https://github.com/l3a0/ithildin-runtime/issues/10) only in [round 13](https://github.com/l3a0/ithildin-runtime/pull/51#issuecomment-6679696854).

Text bound for an issue goes there as a comment before the push that cuts it, naming its round, its anchor and the finding behind it. Step 7's read of the comments and its sentence on a retried post apply, with those three as the key, and a comment under that key with different text stops the push and is reported.

Before writing a fix, name the cause, and fix that rather than the form the lens tried. A fix for one form draws the next form. On [PR #83](https://github.com/l3a0/claude-plugins/pull/83), one span check for a node hidden in a label took four rounds, because each round patched the form the last one found. Where the subject reads another tool's grammar by patterns, it states from round 1 what it does not read, because every pattern has another form, and a stated limit is a finding only where the statement is false. A limit on anything a role protects stays in review.

1. Apply the fixes on each pull request's branch, in its own checkout. A fix to a rule that touches mechanics or a waiting question listed under the brief's `## Out of scope` stays a guarantee and a pointer, takes no side on the question, and keeps in full what the brief keeps in full, whatever fix a verifier proposed.
2. Where the change cites a source, recheck every citation against it with the brief's helper, whether or not a lens flagged it, and list each miss.
3. Where the fixes change code, show the test catches what it claims by breaking the code, with the `fast-mutation` skill or a fixture the code fails on before the fix.
4. Run every check the repository's CI workflow runs, such as this repository's `.github/workflows/board-guard-test.yml`, and note what each printed.
5. Commit, naming in each message the round it answers. Before pushing, run the script below over every pull request, from the round's anchor to the new commit. It prints each run of words the fix removed and each file, in any checkout, that still holds five of them in a row. Check the cuts and moves kept for the comment against the runs, and read each `still in` line. A line on a companion that carries the rule is a cut not yet made there, unless the fix moved the words or the companion keeps them on purpose. Then push.

   ```bash
   python3 <this skill>/scripts/removed_text.py <checkout>=<anchor>..<new commit> <companion checkout>=<anchor>..<new commit>
   ```

   Run over the fixes of l3a0/ithildin-runtime PR #51's round 10, it shows a sentence cut from the design and still in the plugin's risk engineer, which round 11 raised as a must-fix. Run over round 13's, it prints the words on working orders that the comment left out, which round 14 raised.
6. Watch the pull request's checks until they settle, with `gh pr checks <n> --watch`, and fix any red one before posting.

Read each pull request's state with `gh pr view <n> --json state` before pushing, because the owner can merge at any round. A commit pushed to a merged pull request's branch reaches nothing, and on [PR #80](https://github.com/l3a0/claude-plugins/pull/80) a round's fixes sat there until [PR #83](https://github.com/l3a0/claude-plugins/pull/83) carried them. Once one has merged, the fixes go on a new pull request from `main`, and the round's comment goes there.

## 6. Price the round and decide whether another follows

Price the round before posting, so each comment goes out once and complete. Run the plugin's `l3a0:loop-cost` skill over the transcripts of this round's lenses and verifiers, found by the `review <tag> r<N>` descriptions. Give the lenses and the verifiers a line each and then their sum. Price any other loop that served the round on its own line, such as agents that read a source for the change. List only loops this round ran. An earlier round's figures were already posted, and repeating them would count them twice in the `## Cost total` that sums every `## Cost` comment. That is why a round's figures say "this round" where the `l3a0:loop-cost` skill's handover comment says "to date". Main-thread checks run in the session's own context, which these figures leave out, so the comment says so when step 4 used them.

Then decide whether another round follows. A round's fixes are code no lens has read, so the review goes on while anything significant is left, on the owner's ruling of 2026-11-03 that reviews continue until nothing significant is left. The rounds have no fixed count. When a round confirms a veto or a must-fix, in full or in the part a PARTLY verdict held, another round follows, anchored at the fixing commit, from step 1. One exception keeps the rule from running without end on code, because a test engineer can always name a survivor. A round starts no successor when every veto and must-fix it confirmed claims only a missing test or only a false or missing statement about what the subject does, and every fix for them only adds that test or corrects that statement. The session shows each new test failing on the mutant that raised it, and the comment says so and names those fixes for the owner to read first. The exception never covers a wrong result or a weakened guarantee answered by stating a limit, any other veto, a change to any rule the subject writes, or a fix on the path to an irreversible action, whether code, a test of it or a test helper. Those start a round with the required seat. The first round that confirms neither, or that starts none this way, is the last. Its should-fixes are applied as step 4 says and pass step 5's checks, and its comment says that no lens read them. A should-fix can still change what a rule requires. On [l3a0/ithildin-runtime PR #28](https://github.com/l3a0/ithildin-runtime/pull/28), round 1's should-fixes to the loss stop's unwind and to which cancels are exempt each drew a must-fix in round 2, which ran because round 1 also confirmed a veto. So the last round's comment names any should-fix in step 4's class, with whether a verifier read its fix, any removal or move, any fix changed to read an existing record, and any fix this step's exception covers, for the owner to read first.

A finding that only the owner's written ruling can settle, such as a veto the session cannot fix and only an override would lift, goes under `### For the owner`, in the form `SKILL.md`'s step 6 gives, with the line that it waits for the ruling. It does not by itself start a round, and the other findings in its round still do. A question under that heading without that line holds nothing open. While a finding waits, each round's comment takes the round heading. A veto the owner has overridden in writing on the pull request no longer counts as confirmed. A commit that applies the ruling is a fix like any other, so it starts a round when it answers a veto or a must-fix, under the same exception. Once nothing is left that starts a round or waits, the session posts the closing comment described below.

The owner can also end the review at any round by writing so on the main pull request. A confirmed veto still blocks the handover until it is fixed or overridden in writing, under `SKILL.md`'s step 5. Once no veto is left, the session posts the closing comment.

The closing comment takes the final heading `SKILL.md`'s step 6 gives and goes on every pull request of the round, after the last push. It names the round it closes and that round's anchor, and the head where fixes followed that anchor, links that round's comment and the owner's words, and says when fixes were pushed after that round's lenses read the change, so no lens read them. It holds none of the four parts `SKILL.md`'s step 6 lists, because the round's comment already carries them. Moment 5 of the `update-build-board` skill follows it on each pull request, then the handover. Step 8 adds no revision line for it. The round's `## Cost` comment already stands, so where the session also built the change, it edits that comment to add the build's line, and each loop is counted once. The skill outcome goes where the `l3a0:loop-cost` skill's `## Name what a skill could save` says.

Every round posts its comment and its cost as it lands, under step 7, so the owner sees what each round found and spent, and the owner's power to end the review is what bounds its spend. A session that sees one part of the change fail review in successive rounds may also ask the owner, under `### For the owner`, whether that part should be settled on its issue instead. On [l3a0/ithildin-runtime PR #28](https://github.com/l3a0/ithildin-runtime/pull/28), each of the first three rounds raised new findings in the release handover's mechanics, which the design otherwise left to [l3a0/ithildin-runtime #10](https://github.com/l3a0/ithildin-runtime/issues/10).

## 7. Post the review comment

Before posting, check that each pull request's head is the commit the comment will name, with `gh pr view <n> -R <repo> --json headRefOid`. That is the fixing commit, or the anchor where the round changed nothing on that pull request. On any mismatch, post nothing on any of the companions until it is resolved. Read each pull request's comments first too, and skip one that already carries this round, anchor and heading, because a retried post must not land twice. `scripts/review_post.py` does both, for every companion at once. It takes the heading from each file's first line.

```bash
python3 <this skill>/scripts/review_post.py comment --round <N> \
  l3a0/ithildin-runtime#27=<head>=<anchor>=<comment file> l3a0/claude-plugins#48=<head>=<anchor>=<comment file>
```

The script counts only comments by the session's own login, because anyone can comment on a public pull request. A retry that finds the same key with other text stops every post, and the session reports it. A pull request that holds the comment other than once does not stop the others, and the script exits non-zero naming it, so the session deletes the extra copy and reports it. A closing comment that replaces one already posted goes by hand. GitHub takes no key on a comment, so all of this narrows the window for a double post rather than closing it.

Post one comment on each pull request, from `templates/review-comment.md`. On the round step 6 named the last, the first line is the heading `SKILL.md`'s step 6 gives for a final comment. On an earlier round, and on a round that waits for the owner, it is `## Review, round <N>`. The closing comment step 6 describes also takes the final heading. The `working:build` label keeps the card out of the owner's column until the handover, and a board set to read only the final heading also ignores the round heading. Every comment but the closing one holds the four parts `SKILL.md`'s step 6 lists, laid out as the template's sections. A quoted command uses a path relative to the repository or a placeholder such as `<scratch>`, never an absolute local path, because the comment is public.

One pull request is the main one, where the change starts, such as the l3a0/ithildin-runtime pull request whose rules the plugin's role checks carry. Each companion's comment lists the findings fixed there, says where the owner's questions sit, and gives the cost in one line pointing to the main pull request. Where the pull requests track issues, post the `## Cost` comment `SKILL.md`'s step 6 asks for on the main pull request's issue alone. Its first line after the heading is `Review round <N>, of <anchor>, on <pull request link>`, and before posting the session reads the issue's comments and skips the post when one already carries that line. Each companion's issue gets a one-line pointer that does not start with `## Cost`, so a `## Cost total` never reads it. A companion built in its own session still posts its own build's cost on its own issue. None of the worked examples tracked an issue, so this branch has not yet run.

After each round's comment, run the `update-build-board` skill's moment 5 for each pull request on a board. Run its moment 4, the handover, only after the last round. Moment 4's `## Cost` comment is the last round's own, not a second one, so on that round add the build's line to it when the session also built the change. ## 8. Record the revision and the owner's rulings

The pull request body keeps a `## Revision` section, with one numbered line per round. Each line names the fixing commits, the round and anchor they answer, and in a sentence what changed. It ends by saying the review comments list each finding and what was refuted. Update it on every pull request the round changed, and write no line on one it did not change. Do it with `scripts/review_post.py`, which adds the next numbered line. The line goes in a file rather than on the command line, because a line holding backticks and apostrophes can run in the shell. A line reworded after a first send uses `--replace <item>`, because the script recognises a retry only by the whole line.

```bash
python3 <this skill>/scripts/review_post.py revision l3a0/claude-plugins#48 --scratch <scratchpad> --file <file with the line>
```

Its docstring lists what it checks. It narrows the window for an edit the owner made meanwhile rather than closing it, because `gh pr edit` sends no check of what it replaces. When it stops on a body that read back differently, read the body and report it, and resend nothing from the old copy. A body fix a review confirmed elsewhere goes as its own edit by hand, and so does a line the script says to edit by hand. Read that body with `--json body` and parse the JSON, because `--jq .body` prints one newline more than the string holds. Save it, diff the new body against it, and name the lines the fix changes. Re-read the body just before sending, and read it back afterwards and compare it with what was sent. On a mismatch, read it again, stop and report it, and resend nothing from the old copy. Never find a line with a pattern run over the whole body, because the body's other numbered lists use the same numbers. In round 3 on [l3a0/ithildin-runtime PR #28](https://github.com/l3a0/ithildin-runtime/pull/28), a regular expression that replaced the first line starting `2. ` overwrote item 2 of the `## What` list on both companions, and round 4 restored them from GitHub's edit history.

An owner's ruling on a question from `### For the owner` sits where the owner wrote it, on the issue when there is one, as `SKILL.md` says. Post a comment on the pull request where the question sits, starting with the date, such as `Owner ruling, <YYYY-MM-DD>:`. It links the owner's own words, or says it is relayed from the owner's chat of that date, names the commit that applies the ruling, or says that none does, and says which of the review's questions are settled and which are still open. A ruling relayed from chat also goes as a dated line on the issue that owns the question, when there is one, and a refused post is reported under `### For the owner`. A relayed ruling carries no credential, token or account number, and one on a veto also meets `SKILL.md`'s step 5. A companion whose change follows from the ruling gets a comment naming the commit there. Before either post, read the pull request's comments by the owner's login, because another login's comment is not a record, and skip it when one already carries that date, commit, question and words. Where the date, commit and question match and the words differ, post it beside the first, name the earlier comment, and report the difference under `### For the owner`. Neither record replaces the other until the owner says which stands.
